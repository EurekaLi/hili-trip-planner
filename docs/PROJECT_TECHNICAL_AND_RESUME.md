# HiliAgents 智能旅行助手：项目技术复盘与简历材料

## 1. 项目定位与当前状态

本项目从旅行规划学习模板演进为一套可运行、可验证、可编辑的多 Agent 旅行规划
系统。系统以 HiliAgents 作为 Agent 框架，通过高德地图 MCP 获取 POI、天气和路线
事实，再由确定性行程优化器完成时间、地理位置和营业约束校验，最终生成带地图路线、
逐日时间轴、费用估算和来源标记的旅行方案。

当前项目已经完成 Docker Compose 发布形态下的前端、API、Celery Worker、Redis、
PostgreSQL、数据库迁移及可观测组件联调，并通过健康检查、真实行程生成、备份恢复、
回滚、安全响应头、公开读接口压测和浏览器端 E2E 验收，可以表述为“达到可发布、
可演示状态”。尚未完成的工作主要是公开生产环境部署、干净环境 CI 全流程复验、密钥
与 Git 工作区收尾，因此不应表述为“已在公网生产环境长期运行”。

## 2. 项目背景

### 2.1 项目目标

将传统的“LLM 输出一段旅游建议”升级为一套能够实际执行的旅行规划产品：

- 使用真实 POI、天气、开放时间和导航路线约束行程，降低地点虚构与路线不可达风险。
- 根据旅行天数、用户偏好、游览时长和空间分布安排景点，避免某天过空或行程过载。
- 支持异步生成、实时进度、失败恢复、编辑、版本、分享和导出，形成完整用户闭环。
- 对外部 API、模型 Token、图片请求和任务执行设置预算、限流与熔断，控制运行成本。
- 建立测试、监控、备份、恢复和回滚证据，使项目能够被部署、维护和持续演进。

### 2.2 目标用户

- 希望快速得到可执行多日行程的自由行用户。
- 需要基于预算、偏好、交通方式和日期调整行程的深度规划用户。
- 希望保存历史方案、跨设备查看、局部修改并分享给同行人的注册用户。

### 2.3 业务痛点

| 痛点 | 直接影响 | 项目方案 |
| --- | --- | --- |
| LLM 容易生成不存在或不匹配的地点 | 计划不可信 | 高德候选集白名单、POI ID 回填、事实来源标记 |
| 多日行程容易时间冲突、跨区折返 | 计划不可执行 | 确定性时间轴、营业约束检查、真实路线评分和地理分组 |
| 生成耗时长且容易超时 | 页面阻塞、用户重复提交 | Celery 异步任务、Redis 状态、SSE 进度、幂等键和取消机制 |
| 外部服务存在超时、限额和计费 | 稳定性与成本不可控 | 调用预算、超时、缓存、重试、共享熔断和审计指标 |
| 修改某一景点后容易破坏整条行程 | 编辑成本高 | 不可变版本、乐观锁、局部重排和路线/时间轴增量刷新 |
| Demo 缺少账户、部署和运维能力 | 无法形成产品闭环 | 用户生命周期、Compose、监控、备份恢复与发布门禁 |

## 3. 系统设计

### 3.1 总体架构

系统采用“多 Agent 控制层 + 可信数据层 + 确定性优化层”的混合架构。LLM 负责语义
理解、偏好筛选和内容组织，地图与数据库提供事实，普通程序负责约束校验与可重复计算。

| 层次 | 主要技术 | 职责 |
| --- | --- | --- |
| Web 展示层 | Vue 3、TypeScript、Vite、Ant Design Vue、高德 JS API | 参数输入、任务进度、地图路线、行程编辑、分享与导出 |
| API 接入层 | FastAPI、Pydantic | 参数校验、鉴权、限流、任务接口、SSE、管理与合规接口 |
| 异步任务层 | Celery、Redis | 任务排队、状态机、幂等、取消、重投递和实时进度 |
| Agent 控制层 | HiliAgents、Planner Agent、3 个 Stateless Control Agent | 并行分析景点、天气和住宿，汇总为结构化规划输入 |
| 可信数据层 | 高德 MCP、Wikimedia Commons、Unsplash | POI、天气、路线、详情与图片事实 |
| 行程领域层 | Pydantic、确定性优化器 | 候选校验、地理分组、时间轴、开放时间、路线和预算计算 |
| 持久化层 | PostgreSQL、SQLAlchemy、Alembic | 用户、行程、版本、分享、反馈和审计数据 |
| 稳定性与运维层 | Prometheus、Grafana、Sentry、结构化日志 | 指标、告警、链路定位、成本与外部依赖健康度 |
| 发布层 | Docker、Docker Compose、Nginx | 镜像构建、同源反向代理、健康检查、迁移与服务编排 |

### 3.2 多 Agent 设计

系统保留多 Agent，但将 Agent 从“直接获取原始数据的工具层”提升为“使用可信数据做
决策的控制层”：

1. 数据服务先调用高德 MCP，获取受控数量的真实候选 POI、天气和住宿数据。
2. 景点、天气、住宿 Control Agent 使用无状态上下文并行分析候选集。
3. Pydantic 契约解析各 Agent 输出，记录耗时、Token、估算成本和失败原因。
4. Planner Agent 根据结构化结果生成初步多日方案，不直接虚构新的 POI 事实。
5. 系统将 Agent 输出重新映射到候选集，通过 POI ID、名称和坐标完成真实性回填。
6. 确定性优化器处理分组、顺序、通勤、营业时间和时间轴，形成最终可执行方案。

这种边界保留了多 Agent 的专业分工和并行能力，同时避免让 LLM 承担路线计算、时间
运算和数据库一致性等不擅长的工作。

### 3.3 核心数据流程

```text
浏览器提交需求
  -> FastAPI 参数校验、身份识别、限流与验证码策略
  -> Redis 创建幂等任务，Celery Worker 异步消费
  -> 高德 MCP 获取 POI / 天气 / 住宿候选事实
  -> 3 个无状态 Control Agent 并行分析
  -> Planner Agent 生成结构化初稿
  -> POI 白名单校验与真实字段回填
  -> 行程优化器进行地理分组、路线评分、时间轴和预算计算
  -> Redis 更新进度，PostgreSQL 保存行程与版本
  -> SSE / 轮询向前端返回进度和结果
  -> 前端展示地图、路线、时间轴，并支持编辑、分享和导出
```

结构化日志以 `request_id`、`job_id` 和外部调用名称串联执行过程；Prometheus 统计请求、
任务、外部依赖、成本和熔断状态，Sentry 用于捕获未处理异常。

### 3.4 核心数据契约

- API 输入由 Pydantic 校验日期、城市、偏好、预算、交通方式和每日可用时间。
- Agent 输出必须符合结构化模型，禁止把自由文本直接作为业务对象写入数据库。
- POI、路线、天气字段统一执行空值、列表/对象差异、数值和日期时间清洗。
- 数据字段附带 `verified`、`estimated` 或 `unknown` 语义，区分真实事实与模型估算。
- `datetime`、枚举和嵌套模型在任务边界统一转换为 JSON 可序列化数据。
- 营业时间跨午夜时按业务语义处理，避免简单的“关闭时间必须大于开放时间”误判。

## 4. 核心开发工作

### 4.1 地图与外部数据接入

- 打通高德 MCP 的 POI 搜索、详情、天气、步行/公交等路线接口，统一解析 MCP 文本、
  对象和异常响应。
- 维护项目内的 `amap-mcp-server` fork，修复坐标路线工具调用和标准输入输出问题，避免
  直接修改可能被重建的 `uv` 缓存。
- 为外部调用增加调用次数、耗时、超时、错误分类和成本审计，支持按任务查看资源消耗。
- 建立“高德 POI 图片 -> Wikimedia Commons -> Unsplash -> 本地占位图”提供链，加入
  缓存、并发限制、来源署名和降级策略。

### 4.2 多 Agent 编排

- 实现无状态 Control Agent，每次仅使用系统提示词和当前任务输入，避免不同用户或任务
  共享历史上下文。
- 使用线程池并行执行景点、天气和住宿 Agent，缩短串行等待时间。
- 设计结构化 Agent 输出契约、真实候选白名单和错误隔离，单个辅助 Agent 失败时可降级，
  Planner 仍可使用其余可信数据完成规划。
- 保留完整规划提示中的时间安排、餐饮、住宿、交通和预算细节，并增加事实边界、POI ID、
  每日游览时长覆盖和 JSON 输出要求。

### 4.3 行程优化算法

- 比较 Planner 原始分组与地理优化分组，按真实路线时长、跨区域惩罚、不可达回退和时间
  冲突计算方案得分。
- 对接近全天游览时长的景点进行单日隔离；其他景点先按最近邻生成候选链，再使用动态
  规划按每日目标游览时长切分。
- 基于开放时间、闭馆日期、用餐时段、景点游览时长和路线时长生成确定性时间轴。
- 设置路线调用缓存和单任务最大调用次数，控制高德接口费用与整体延迟。
- 用户替换景点或跨日拖动后，仅重算受影响日期的路线和时间轴，避免整份行程重新调用 LLM。

### 4.4 异步任务与可靠性

- 将长耗时生成流程改为 Celery 异步任务，API 立即返回 `202` 和任务标识。
- 使用 Redis 保存任务状态、阶段进度、版本号和最终结果，前端通过 SSE 接收变化事件，
  同时保留状态查询作为断线恢复手段。
- 引入幂等键，阻止重复请求创建多份计费任务；支持用户取消和终态一致性检查。
- 对 Worker 丢失、消息重投递和外部依赖异常设置执行权、重试和恢复规则，降低重复执行风险。

### 4.5 用户闭环

- 支持游客草稿、注册登录、游客数据认领、跨设备历史行程和账户注销。
- 使用不可变版本与乐观锁处理并发编辑，支持景点替换、跨日拖动、地点锁定和局部重排。
- 支持分享链接及撤销、用户反馈、PDF/ICS 导出和高德导航 URI。
- 记录敏感操作和版本变化，保证修改过程可追踪。

### 4.6 安全、成本和可观测性

- 实现服务端会话、角色权限、注销二次确认、请求体限制和 Redis 分布式限流。
- 支持 Turnstile 人机验证，防止生成接口被批量滥用。
- 为 LLM、地图、图片和总体费用定义单任务预算，并使用 Redis 共享熔断器隔离故障依赖。
- 输出结构化日志，暴露 Prometheus 指标，提供 Grafana 监控入口和可选 Sentry 异常上报。
- 管理端可查看任务、外部调用、成本、失败原因和熔断状态。

## 5. 项目演进流程

项目按风险从核心链路到发布能力逐步推进：

1. **真实数据接入**：先替换 POI、天气和路线空数据，建立高德响应适配与字段清洗。
2. **Agent 边界治理**：保留多 Agent，将其改造成无状态并行控制层，禁止越过真实候选集。
3. **可执行行程**：加入确定性优化器、开放时间约束、路线几何和逐日时间轴。
4. **异步与可靠性**：引入 Redis、Celery、SSE、幂等、取消、重试和故障恢复。
5. **用户产品闭环**：完成账户、历史、版本编辑、分享、反馈与导出。
6. **安全与成本治理**：补齐限流、验证码、预算、熔断、日志、指标和管理端能力。
7. **发布工程化**：建设分层测试、Docker Compose、迁移、健康检查、备份恢复和回滚门禁。

## 6. 数据与测试

### 6.1 数据处理策略

- 对地图返回的字符串、空列表、缺失字段和嵌套结构进行标准化，避免供应商响应直接渗透
  到业务层。
- 以 POI ID 和坐标作为主要事实标识，名称相似匹配仅作为受限回退策略。
- 对 Agent 输出执行 Schema 校验、候选白名单校验、时间冲突检查和 JSON 序列化测试。
- 对路线和图片结果设置缓存；对无法验证的数据显式降级，而不是伪造完整字段。
- 使用固定城市/日期数据集评测可执行日比例、路线覆盖、游览覆盖、时间重叠和最长通勤。

## 7. 部署与优化

### 7.1 发布架构

- 后端和前端使用多阶段 Dockerfile 构建，运行阶段使用非 root 用户并尽量减小镜像内容。
- Docker Compose 编排 PostgreSQL、Redis、迁移任务、FastAPI、Celery Worker 和 Nginx Web；
  可选 profile 启动 Prometheus 与 Grafana。
- Nginx 提供静态资源、同源 API 反向代理和安全响应头，降低跨域配置复杂度。
- API 提供 liveness/readiness 检查，readiness 同时检查数据库和 Redis 依赖。
- Alembic 在应用启动前执行迁移；发布使用不可变版本号，支持数据库备份、校验、恢复和版本
  回滚演练。

### 7.2 稳定性与性能优化

- Control Agent 并行执行，降低景点、天气和住宿分析的串行耗时。
- 路线与图片缓存、按需详情查询和调用上限减少重复外部请求与付费调用。
- 异步任务将长耗时操作移出 HTTP 请求周期，SSE 只在任务修订版本变化时发送消息。
- Redis 共享限流、预算和熔断状态，保证多 API/Worker 实例采用一致控制策略。
- 前端路由按页面拆分，PDF 相关依赖独立成块，并设置总产物与单块预算。
- 结构化日志、指标和错误上报让超时、失败供应商和高成本任务能够被定位。

### 7.3 发布状态与剩余收尾

已经具备：本地生产形态启动、真实生成链路、健康检查、数据库迁移、备份恢复、回滚演练、
监控入口及跨栈发布测试。

正式对外部署前还应完成：

- 清理并轮换可能进入本地 Git 工作区的真实密钥，确保 `.env` 不被跟踪。
- 将高德 MCP 子模块提交固定到 fork 的可复现版本，并让 CI 递归检出子模块。
- 在全新 Runner 上完成 Linux 锁文件安装、全量 CI、Gitleaks、Trivy 和 Live Contract 门禁。
- 选择云环境部署 TLS、域名、持久卷、备份保留策略、告警接收人与 SLO。
- 继续拆分接近预算阈值的前端主包，并以多次真实生成样本建立成功率、P95 和单次成本基线。
- 项目成熟后按 ADR 将应用从示例目录提取为独立仓库，形成独立版本与发布周期。

## 8. 关键技术取舍

### 为什么不让 LLM 直接输出最终行程

LLM 擅长偏好理解和语义组织，但不擅长精确时间运算、最短路径和事务一致性。项目采用
“LLM 提议、真实数据约束、确定性程序裁决”的方式，使同一输入的关键约束可测试、可
解释，也能在用户编辑后局部重算。

### 为什么继续使用多 Agent

景点筛选、天气影响和住宿选择拥有不同上下文和评价目标，拆分后提示词更聚焦，也可并行
执行。无状态 Agent、结构化契约、共享预算和最终 Planner 汇总控制了上下文污染、费用和
输出不一致问题。

### 为什么使用异步任务而不是增加 HTTP 超时时间

真实行程需要多个地图与模型调用，耗时不可稳定预测。单纯增加 HTTP 超时会占用连接、
鼓励用户重复提交，并难以恢复。任务队列允许排队、取消、重试、进度反馈和断线后继续查询。
